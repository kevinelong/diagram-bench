# Comparing two machines: UI/UX and LLM (2026-11-02)

Two machines run this app and this pipeline: the desktop here and the RTX 4060 laptop. This page is what a comparison
has to record to mean anything, what is already measured, and what is still unknown. It exists because "the laptop feels
slower" is unfalsifiable, while "`folder_click_to_pane` 259 ms here, not recorded there" is a work item.

**Correction to an earlier note.** Compute 12.0 / FP4 *native* is **this** desktop (RTX 5070, Blackwell), not the laptop;
the laptop is compute 8.9 with FP4 *emulated*. The two are not the same generation and the 10x render gap below follows
from that, not from power settings.

## 2. UI/UX performance: what to measure

A user interface is fast or slow in units of **how long an interaction makes the reader wait**, and the thresholds are
old and stable (Nielsen): **0.1 s** reads as instant, **1 s** keeps the flow of thought, **10 s** loses attention. So the
metric set is interaction latencies, not benchmark scores. The app already records exactly the ones that matter, through
`PROFILE` (`_Profile.record`), so both machines can produce the same table:

| event | what it means to the reader | budget |
|---|---|---|
| `folder_click_ack` | the click was visibly received (label/cursor, before any work) | **< 20 ms** |
| `folder_click_to_pane` | the folder's pictures are on screen | **< 1 s**, ideally < 400 ms |
| `render_contents` | building one page of the pane (`BATCH_CONTENTS`) | **p90 < 250 ms** |
| `apply_strip_resize` | the gallery strip reflowed after a resize | **< 200 ms** |
| `refresh_gallery` | the whole strip was rebuilt | **< 300 ms** |
| event-loop stall | longest gap between Tk callbacks while a job runs | **< 100 ms** |

### Measured on this desktop (real gallery: 2,736 pictures, 106 folders)

Re-measured 2026-11-02 on **v0.20.0** over the real gallery (2,935 pictures, 102 folders, worst folder **601**) with
`tools/ux_timing.py` - five large folders in sequence, which is the interaction a reader actually performs:

|---|---|---|---|---|

**Side by side, same worst folder:**

| event | laptop | desktop | ratio |
|---|---|---|---|
| `folder_click_ack` | 0.6 ms | 2.3 ms | **0.26x - laptop faster** |
| `apply_strip_resize` | 48.5 ms | 115.9 ms | **0.42x - laptop faster** |
| `folder_click_to_pane` | 283.6 ms | 722.9 ms | **0.39x - laptop 2.5x faster** |

**What that says.** "The laptop feels slower" is **wrong about the work and right about the strip**: opening a 540-picture
folder is **2.5x faster here**, and so is a sash resize; what costs 1.9 s is `refresh_gallery`, the whole-strip rebuild
that runs *inside* every folder click. The desktop's own note already identified that call (`PLAN §11.2`); this
measurement adds that it is **3.8x worse on the laptop** while everything around it is better.

**A cliff worth recording.** The first run on this box used a gallery whose grouping collapsed to 5 folders with a
**1,002**-picture worst folder, and `folder_click_to_pane` was **11,718 ms p50 / 44,060 ms p90**. Doubling the worst folder
from 540 to 1,002 multiplied the pane cost by **41x** - that is not a curve, it is a threshold, and it is the most
important number on this page for anyone with a big folder.

**Two limits of this run.** The tool's `warm_pass` records no events (only `open_wall_ms`), on both runs here, so the
warm figures above are the cold pass's; and the folder count is 22 against the desktop's 102, which is why
`refresh_gallery` cannot be read as pure per-picture cost.

### How to record it: one command, both machines

A paragraph is not an instrument, so the measurement is `tools/ux_timing.py`. It boots the app against a gallery with a
stub engine (no GPU, no ComfyUI, no model), opens the **five biggest folders**, resizes the window four times, and prints
one JSON block: the machine's CPU/cores/RAM/GPU/driver/compute, the app version, the gallery shape, each event's
`n / p50 / p90 / max`, a **cold pass** and a **warm pass** (the first pass pays scans and thumbnail builds; averaging them
in would hide both), and the calculated comparison figures.

```powershell
python tools/ux_timing.py --source C:/Users/kevin/Pictures/zimage-ui --json ux-desktop.json
```

Read-only: settings go to a temp dir, the gallery is never written, nothing is loaded.

### This desktop, measured with it (2026-11-02, v0.17.0, 2,874 pictures / 102 folders / worst folder 540)

| event | n | p50 | p90 | budget | verdict |
|---|---|---|---|---|---|
| `folder_click_ack` | 5 | **2.3 ms** | 2.5 ms | 20 ms | instant |
| `apply_strip_resize` | 5 | **115.9 ms** | 198.8 ms | 200 ms | in flow |
| `refresh_gallery` | 5 | **515.1 ms** | 576.5 ms | 300 ms | **fails** |
| `folder_click_to_pane` | 4 | **722.9 ms** | 760.4 ms | 1 s | in flow, but close |

`budget_compliance: 3 of 5`; jitter p90/p50 is 1.05-1.72 (the resize is the jittery one).

**What that measures that a single click did not.** The 259 ms reported after the page cap was *one warm folder*. Navigating
five big folders in sequence costs **723 ms p50**, because every folder click runs `refresh_gallery` (515 ms) inside it -
that is `PLAN §11.2`'s number, now reproducible with a command rather than by reading a log. The cold pass is 844 ms on the
same folders, so the gap between cold and warm is real but small: the cost is the rebuild, not the cache.

## 3. LLM performance: what to measure

For a UI that drives a model, the reader experiences two numbers, and they map straight onto the thresholds above:

| metric | meaning | budget |
|---|---|---|
| **TTFT** (time to first token) | prefill + first decode step | **< 1 s** feels conversational; 3 s feels like a job |
| **decode tok/s** | reading speed after the first token (~4 chars/token) | **> 15** keeps up with reading; > 40 is fluent |
| **prefill tok/s** | prompt processing, so long context does not stall TTFT | reported with the context length that produced it |
| peak VRAM | does it fit, and what is left for the UI | under the card, with headroom |

Report tok/s **with the context length and the quantisation**, or the number is not comparable.

### Measured on this desktop

| what | value | source |
|---|---|---|
| CPU MoE decode, 256-token decode | **30.4 tok/s @ 8 threads, 32.3 @ 16, 29.5 @ 24** | lab notes, measured 2026-10-19 |
| diffusion, z-image turbo 1024 px, 9 steps | **14.3 s** | `README`, deployments table |
| diffusion, same job on the 4060 laptop | **142.5 s** (10x) | `README` |
| `flux2 klein 9b` 512 px on the 4060 laptop | **does not fit** (8,837 MiB peak on an 8 GiB card) | `README` |

Two things follow. The **10x** diffusion gap is a compute-generation effect (12.0 with native FP4 vs 8.9 with emulated
FP4), not a settings question. And CPU decode saturating at 16 threads, then falling back at 24, is a **memory-bandwidth
wall** (dual-channel DDR5-6400, ~102 GB/s theoretical), not a core-count one - so GB6 multi predicts nothing about it.

### On the laptop: token rates unknown

Nothing records TTFT or tok/s for that box. It runs the same models at 8 GiB, so the interesting number is not "faster or
slower" but "what fits, and what is TTFT at that size".

### How to record it (either machine): `llama-bench`, not a stopwatch

`llama-bench` is the only instrument here that reports both halves in one run, at a stated context, so two machines can be
compared without arguing about the harness:

```powershell
llama-bench -m model.gguf -p 2048 -n 128 -t 16          # pp2048 and tg128 at the model's default ctx
llama-bench -m model.gguf -p 8192 -n 128 -t 16 -c 16384 # the same at a long context
```

| reported | means | use it as |
|---|---|---|
| `pp2048` (tok/s) | prompt processing | **TTFT for a 2k prompt ≈ 2048 / pp2048** seconds |
| `tg128` (tok/s) | decode | reading speed; **> 15** keeps up with a reader |
| VRAM peak (from a real run, not the bench) | headroom for the UI | must leave room for this app's own thumbnails |

Record model file name, **quantisation**, `n_ctx`, thread count and driver version beside the two numbers. A tok/s without
them is not comparable - the same card can differ by 2x across quants.

## 3a. The cliff: not reproduced here (2026-11-02)

The 4060 box reported a **1,002-picture** worst folder costing `folder_click_to_pane` **11,718 ms p50 / 44,060 ms p90** —
41x the 540-picture cost for twice the pictures. Synthesised here with `tools/make_ux_gallery.py` (1,600 pictures, worst
folder 1,095) it does not happen:

| folder | window | `folder_click_to_pane` | `render_contents` | prefetch |
|---|---|---|---|---|
| **1,095** pictures | 1600x1000 | **224 ms** | 224 ms | 174 ms (idle) |
| 127 pictures | 1600x1000 | 127 ms | 127 ms | - |
| **1,095** pictures | **1280x800** (the laptop's size) | **160 ms p50 / 316 ms p90** | 160 ms | - |

So the cost is not the folder size, not the window size, and not the page cap (96 tiles) - the same 1,095-picture folder
costs 160-224 ms here. What differs on that box and cannot be reproduced from this side: 125 % DPI (Tk scaling runs through
the same metrics as the floors), a cold thumbnail build for the first page on a slower CPU, its own ComfyUI/Ollama
contention, and ranking/pair state that a synthetic gallery does not carry.

**It is per image, not per folder - which the arithmetic in their own numbers shows.** One page is 96 tiles, so:

| box | 1,000-ish folder | per tile | cache |
|---|---|---|---|
| laptop | 11,718 ms p50 | **122 ms** | cold |
| laptop (p90) | 44,060 ms | **460 ms** | cold, contended |
| desktop | 224 ms p50 for 1,095 pictures | **2.3 ms** | warm |
| desktop, measured directly | 96 tiles | **3.6 ms cold / 0.2 ms warm** | both |

So the unit is the thumbnail, and the laptop's number is a **cache miss for the page** - the same page costs 346 ms cold here.
Their 540-picture figure (283 ms) was almost certainly measured with the cache already warm, which is why 2x the pictures
looked like 41x the work: it was not the folder at all. Their reboot also reset the model store (`qwen3-vl:4b` disappeared),
so the thumbnail cache under the settings directory was likely cold too.

**The mitigation is therefore cache and prefetch, not folder-size tuning:** keep `.thumbs` across runs (and say so when it is
missing), build the first page in the background rather than inside the click, and consider a smaller cold page. None of that
needs the 1,002-picture folder to be split.

**The ask is a measurement, not an answer:** run `python tools/ux_timing.py --source <that gallery> --json ux-cliff.json`
twice on that box and send the JSON. Its event table names the culprit - if `render_contents` is seconds, it is tile
building; if `refresh_gallery` is, it is the scan behind the click; if neither appears, it is outside the profiled paths.

## 3b. What the comparison should calculate

The tool already computes the columns that turn numbers into a verdict; the laptop simply runs it. Beyond that, compute
these by hand when the two JSON files are side by side:

| figure | formula | why it matters |
|---|---|---|
| budget compliance | events with p90 within budget / 5 | the one-line "does this machine feel good" |
| jitter | p90 / p50 per event | a good p50 with 2.0 jitter still feels rough |
| open ratio | `folder_click_to_pane`(laptop) / (desktop) | how much slower navigation is, per click |
| TTFT at 2k | 2048 / `pp2048` | whether the model is conversational on that box |
| decode ratio | `tg128`(laptop) / (desktop) | reading speed, not benchmark speed |
| headroom | (card MiB - model peak MiB) / card MiB | whether the UI has room to render while the model is loaded |

Do not compute a single blended "score". The two machines differ by 10x on diffusion and by roughly nothing on
`folder_click_ack`, and averaging those into one number would hide exactly the thing worth knowing.

## 4. Rules that make a comparison valid

- Same model file, same quantisation, same `n_ctx`, same prompt; report `n_ctx` beside tok/s.
- Same gallery and same folder for UI timings, thumbnails cached or cleared - say which.
- One load at a time; WSL shut down; no second inference (lab rule, not a preference).
- Report p50 **and** p90, plus the sample count. A single click is an anecdote (`PROFILE` prints `n`).
- Note the app version: the pane was rebuilt 22 times per open before `v0.16.1`, so timings from older versions are a
  different program.
