Three changes, mirroring iimage 0.141.0 (a035a45) - "top-bar actions as real buttons", "clipboard paste with a
destination rule", and "create from the picked set" - done in Tk idiom rather than transliterated from the Win32 code.

 2. Paste from the clipboard: one verb, three places, lands in the folder on screen, picked and armed.

1. THE ACTIONS LOOK AND SIZE LIKE BUTTONS
- One measurement, two shared places. `ACTION_PAD_X = 12` / `ACTION_PAD_Y = 6` at the top of the layout constants; read
  by `ActionButton.__init__` (the tk family: Generate, Use as Base, Clear Base, Make clip, Open clip) and by the
  `Action.TButton` style configured in `Theme.apply` (the ttk family: Open…, Paste, ▸ options, Select all, Gallery…,
  A/B…, Recover…, Caption…, Delete…). `action_button(master, **kw)` is the ttk constructor, so a call site can only
  choose the words and the command.
- Resting state: the tk family wears `relief='raised', bd=2`; the ttk family gets the style's surface, bordercolor and
  - on clam, which is what dark mode uses because it is the only bundled theme whose colours can be set - a background
  and a state map. On vista the theme paints its own bevel and ignores the map; the padding is still read, so both modes
  are the same size.
- Hover and press: `activebackground` is set once (hover), and `<Enter>`/`<Leave>`/`<ButtonPress-1>`/`<ButtonRelease-1>`
  repaint the surface so a hover tone exists even where the active colour equals the resting one and the press is
  visibly darker than the hover. The ttk style maps `active` -> theme.hover and `pressed` -> a darker mix.
- Deliberately NOT scaled by the display: this window's geometry is pixels everywhere (sashes, tile floors, pane
  widths) and Tk's scaling factor moves fonts, not pads. The app has no pixel-DPI handling to hook into; inventing one
  for four numbers would be the layout's only scaled value.
- The layout was measured rather than assumed, at the window's own minimum (1200x700) and at 1600x950:
  `source_row` 206 px requested / 407 px of title row; `contents_btns` 257 px requested in a 265 px pane; the picture
  column's action bar is untouched (283 px, its own floor) and the clip row ends at 690 of 700. Two rows deliberately
  keep the default padding: the picture column's action bar (`Vary`, `hires ×2`, `Paste image`) because its 283 px is
  the picture column's floor and padding it would squeeze every other column, and the pane's `⋯` overflow button, which
  is a menu affordance rather than an action in the list.

2. PASTE FROM THE CLIPBOARD
Rules taken from iimage's README ("Paste, and starting from a pick"), translated:
- `ImageGrab.grabclipboard()` is read **once, on the press**. Three shapes, three meanings, all handled:
  * an `Image` (screenshot, browser "copy image") - saved as a PNG;
  * a `list` of paths (Explorer's copy) - pictures to import, **not an error**; every image in the list is written;
  * `None` - text on the clipboard (a copied path that names an image is used) or nothing at all, and only the last of
    those cannot be pasted: `clipboard holds no picture - nothing usable on the clipboard: copy a bitmap, an image
    file, or the path to one`.
  No paint path calls OpenClipboard, so an empty clipboard costs nothing until somebody presses Paste.
- Destination: **the open folder** - the one the gallery is showing (`_source`) - and nowhere else. There is no
  guessing at the render folder when another folder is open. `_paste_target()` returns (folder, reason) and is read by
  the button's state, the picture menu's entry and the action itself, so the three cannot disagree. With no folder it
  is greyed and the status line carries `no folder is open …`, which is also what pressing the verb says if it is
  reached anyway.
- After the write: `refresh_gallery(select=<the new file>)`, then `use_as_base()` - the existing arm-the-base path, not
  a second one - so the file is picked, is the base, and pasting a reference then pressing Generate is one gesture.
  The status line names the file (`pasted <name> - 300x200, now the new base`).
- Naming and collision reuse the app's own convention: `pasted_filename()` is `shot_filename`'s shape for a picture no
  sampler made (`pasted-<stamp>_<w>x<h>.png`; the seed slot is absent because a paste has no seed), and `free_path()`
  settles a collision with `_2`, `_3` - the same `_NN` suffix `shot_filename` already uses for the tiles of one batch.
  Nothing is overwritten: two pastes in the same second are two files.
- Exposure: **Paste** in the top row beside `Open…`, **Ctrl+V** at the window (unchanged binding, the same verb), and
  *Paste a picture from the clipboard into this folder* in a picture's right-click menu.
- Found while doing it: `refresh_gallery(select=...)` accepted a picture and **ignored it** - the parameter had been
  dead since it was added, at this function and at its two callers (a finished render, and the rebuild after a click on
  a tile the strip had not painted). It now selects: the named file, if the folder holds it, is the pick and the anchor.

3. START A GENERATION FROM THE PICKED SET
- **Create New Image based on Selected Images** in the picture menu: live with >= 1 picture picked, greyed with
  `pick at least one picture first` otherwise (the reason also goes on the status line, as for Paste). It opens the
  generator with the pick as its basis and states the count - `creating from 3 selected pictures - numbered
  Image1..3 in the order they were picked; say in the prompt how they go together, then Enter`.
- It does not render, and the acceptance is that it does not: the count and the sentence go to the status line, the
  prompt box takes the keyboard, and `generate` (which already accepts `base_images`) is what renders when a person
  presses it. The arm goes through `use_as_base`, which already put every selection into `_bases`.
- **Why click order matters**: a multi-reference prompt numbers the pictures Image1, Image2 - so "first" has to mean
  the one picked first, and a set cannot answer that (a `set`'s iteration order is not a promise; sorted order would
  mean the alphabetically least file name). `App.selected` is already that list (`_on_tile_click` appends on ctrl-click
  and replaces on a plain one) and `_pick_order_now()` reads it; `ScrollGrid` - which keeps its own `chosen` **set** for
  the grids that do not hand selection to the app - now keeps `picked` beside it, with one `_choose()` writer and
  `picked_order()` as the reader, which is iimage's `selection::Picked` / `picked_order()` in Tk form. The set is kept,
  not replaced: it is still what the rings are painted from.
- **"Mark as best" was deliberately NOT built.** iimage's version records a `vote::record` win against the folder's
  leader and re-ranks; this app has no vote store and no rank to record into. Its existing notion of *best* is the
  **A/B review** (`A/B…` on the folder row, the strip header and a folder tile; decisions go through `pair_review` and
  re-rank the folder - `pair_rank.sort_by_wins` reads them when "wins" sorting is on). A person marks a favourite today
  with **★** (`toggle_star`, then `starred only`), which is a favourite rather than a ranking. Adding a vote table for
  a one-click "best" would be new scope and a second definition of best - the decision is Kevin's, and it needs one of
  those two to become the rank, not a third.

- paste: the picture is written into the folder on screen (not the render folder), its name is the app's shape, it is the
  pick, it is the base through `use_as_base`, the status line names it, and its sidecar says `source: clipboard`;
  a second paste in the same second is a second file and the collision is a `_2`, not an overwrite; with the folder
  gone the button is greyed with `no folder is open` on the status line and pressing the verb writes nothing; an empty
  clipboard says `clipboard holds no picture`.
- the picture menu: `Create New Image based on Selected Images` and the Paste entry exist once each, and Create is
  `disabled` with nothing picked and `normal` with two picked - the same for the status line's sentence.
- click order: three pictures clicked out of file-name order come back in click order, which is asserted to differ from
  the sorted order; `_create_from_selected` puts them into `_bases` in that order, opens the `image` screen, says
  `3 selected pictures`, and renders nothing (the stub engine's call count is unchanged); with nothing picked it returns
  None and says `pick at least one picture`.
- the grid: `ScrollGrid.picked_order()` returns `['c', 'a', 'd']` after those toggles while `chosen` is still a `set` of
  the same three, and a toggle that drops one leaves the order `['c', 'd']`.
- the buttons: the `Action.TButton` padding lookup contains 12 and 6; the seven ttk actions carry that style; the five
  `ActionButton`s are padded 12x6 with `bd >= 1` and `relief=raised`; the hover tone differs from the resting colour and
  the press differs from the hover; and at 1200x700 the padded rows still fit their columns and the clip row still ends
  inside the window.
