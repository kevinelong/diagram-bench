## 2. What changed in the GUI (committed as `35aebaf`, suite green)

Three changes, each one variable and each with the suite run after it.

1. **Destroyed-tile guard** (3 sites, `_scroll_folder_into_view`, `_see_folder`, one more). A strip rebuild
   leaves a queued callback holding a dead Tk window path — that is the `TclError: bad window path name`
   in `%LOCALAPPDATA%/zimage-ui/errors.log` from 2026-10-30, and it is why scrolling/clicks feel dead for a
   moment after any refresh.
2. **The open folder now stays open after a render.** `_show_new_results` used to close it so the brand-new
   (unfiled) picture would be visible; that read as "the folder will not open after a generation". The hint now
   says where the picture is. This was a *tested contract* — three assertions in `test_gallery_ui.py` were
   rewritten to the new behaviour, explicitly.
3. **The seed box advances by the batch, not by one.** `generate()` records `_seed_advance = batch * seed_step`
   (or `seed_step` for a true single-latent batch); the save handler consumes it **once** and resets it to 1.
   A 16-up from seed N now leaves the box at N+16; it used to leave N+1, so the next press re-rendered 15 of
   the same 16 seeds. New coverage: "a 16-up from seed 900 leaves the box at 916".
   The one-shot reset is load-bearing: without it, any save that did not go through `generate()` inherited the
   last batch's step (the suite caught exactly that: 793 instead of 778).

Not changed, and deliberately: `_show_new_results` closing behaviour was reverted once because
auto-reopening the folder inside `_apply_plan` changes what `app._files` holds and broke `test_gallery_ui.py:3649`
with `IndexError`. The adaptive poll (60 ms -> 200 ms idle) was also reverted: it starved the suite's ~50 ms
`root.update()` spins, and it was never proven to be the idle-lag cause.

### Cold-start prewarm (added, not yet proven)

`_prewarm_thumbs()` runs at the end of `refresh_gallery`, once per session, warming the 12 strip thumbnails plus
each folder tile's 4 in a worker thread. Rationale: a tile's PhotoImage is built on the paint path — 13 ms for a
cached-size thumbnail, up to 81 ms for a 6 MB 1536 px render — so a cold start was paying twelve decodes during
the first paint, which is the "twelve blank tiles" in the 2026-10-31 screenshot.
**It shows no delta in the suite** because that temp gallery's thumbs are already warm. Proving it needs a run
against a gallery with no `.thumbs` cache — do not delete the real cache without asking (3000+ files rebuild).

Also diagnosed from the same screenshot: the folder column is empty at start because grouping is still running
(~2.4 s for 1800 prompts). That is not a bug and cannot be hurried; only the blank *tiles* were a defect.

### The regression: "images are not showing as they are generated" was mine

`_visible_files()` scopes the list to the **open folder**, and opening a folder by default meant that scope applied from
the first second of every run. A picture written during a run is not in the plan yet, so it was filtered out of `_files`
before any tile could be drawn. Measured before the fix: a `tile` event called `refresh_gallery`, `_scan()` saw the new
file on disk, and `_files` stayed at 8. The scope is now skipped while `busy` — the state in which the strip draws
pictures rather than folders.

### The instrument that found it

`tools/tile_latency.py` writes realistic tiles into the gallery at a chosen cadence, delivers them through the same
`('tile', ...)` event the engine posts, and reports time-to-painted-picture. It found the bug because its first run
printed `8 of 8 strip widgets` and `16 timeouts`. After the fix:

| payload | median | p90 | max | painted |
|---|---|---|---|---|
| 1024 px, 0.7 s cadence | 0.09 s | 0.11 s | 0.11 s | 16/16 |
| 1024 px, all at once | 0.05 s | 0.08 s | 0.09 s | 16/16 |
| 1536 px, 0.7 s cadence | 0.11 s | 0.16 s | 0.17 s | 16/16 |

`tools/pane_audit.py` is the sibling for "a folder shows nothing": it opens every small folder and prints items,
painted tiles, page size, scrollregion and first-tile y. It is what cleared the four-picture folder as a layout fault.

### The caches, and what they actually bought

- **Plan cache**: written beside the settings, keyed by a sha1 over every picture's name and mtime. A stale signature is
  not applied. 10.4 MB for 1,427 pictures; signature 0.30 s, parse 0.05 s.
- **Heads**: each folder's chosen four are resolved once, stored as `group['head']`, and reused on later paints.
- **Signature memo**: `_signature` is now memoised by mtime instead of being wiped on every refresh, fetches one
  thumbnail instead of spinning a pool, and folder sheets compose from the thumbnail cache only
  (`thumbs_for(build=False)`) — 208 synchronous decodes were the 4.47 s first paint.

Measured on a **frozen 250-picture copy** of the gallery:

| | first plan | folders with cached four |
|---|---|---|
| cold | 6.84 s | 19/19 |
| warm | 4.12 s | painted tiles reuse the cache |

### The three checks that were failing, and what each really said

All three failed at `HEAD` before the upscaler work and are now green (all eight suites exit 0):

1. **sizing "a narrower window re-clamps them instead of overflowing"** — a real bug, not a test artefact. A layout
   remembered on a wide screen kept the prompt column at 1343 px in a 1200 px window, so the four columns summed to
   1629 in 1100. The clamp gave width up from the strip only; it now cascades strip → prompt → pane, each to its floor.
2. **sizing "three across is a wider tile than four would have been"** — a test artefact of the retired rule: with the
   tile capped at the base width, four columns are *preferred*. It now asserts the columns and tile `tile_grid` asks for.
3. **gallery "and the strip scrolled to get there"** — a test artefact. With 24 folders the strip's content is 2048 px
   against a 1295 px viewport, so the deepest possible `yview` is **0.368**; `> 0.5` was never reachable and only
   passed while tiles were small enough to make the content taller. It now asserts the achievable maximum.

### The measurement gotcha that cost an hour

**Never time startup against the live gallery.** The first warm measurement read 8.84 s and looked like a regression in
the new cache; it was a cache *miss*, because the app was writing to that gallery while it ran. Freeze a copy first.

## 13. Perceived speed: acknowledging the click before building it (2026-11-01)

The question was whether *ordering* the work makes the app feel faster. Nielsen's limits are the yardstick (0.1 s feels
instant, 1 s keeps the flow, 10 s loses attention), and the answer is yes: the expensive half was running before any visible
half.

`select_folder()` used to run `_render_contents()` - the pane builder - **before** anything changed on screen. It now
acknowledges first: the folder cursor, the button's label and an "opening…" title, then `update_idletasks()`, then the build.
Two new events record both halves.

Measured on the real gallery (2 491 pictures, 81 folders), ten folder clicks through `tools/real_session.py`:

| event | n | p50 ms | p90 ms | max ms |
|---|---|---|---|---|
| `folder_click_ack` | 10 | **1.4** | 3.3 | 8.3 |
| `folder_click_to_pane` | 10 | 402.1 | 445.2 | 569.5 |

So the click is now visible in ~1 ms and the pane follows in ~0.4 s - inside the 1 s flow limit instead of starting 0.4 s
late. That is the reordering: the same work, a different first half.

**What it does not fix, and one thing it exposed.** A cold-app click measured **2 076 ms** end to end; the profile shows where:

| event | n | ms |
|---|---|---|
| refresh_gallery | 1 | 1 655.7 |
| apply_strip_resize | 1 | 547.4 |
| folder_click_to_pane | 1 | 419.2 |
| folder_click_ack | 1 | 0.8 |

## 18. Sashes: what governed them, and why they felt random (2026-11-02)

**What they are called.** Tk's own name for a draggable divider between panes is a **sash** (in `PanedWindow`); this app
builds its own `Sash` widget, 8 px hit area, cursor `sb_h_double_arrow`, a 2 px **grip** that tints on hover/drag/focus,
Left/Right ±16 px (64 with Shift), Home/End to the ends, double-click back to the default. Three of them: `strip` (strip vs
pane, inside the gallery column), `gallery` (gallery column vs prompt), `prompt` (prompt vs picture).

**The rules that made it feel random.** Two of them were arbitrary and one was not:

* `strip` floor was `GAL_FLOOR_W + bar` - about 400 px, four columns at the narrowest tile - and pane's was
  `CONTENTS_W_MIN` 180, so the boundary stopped far from where the pointer was going; the pane cap was 480 and the strip
  cap 990, so a wide window could not give either more.
* the `gallery` sash traded two columns at once and the **pane paid before the strip**, so mid-drag the trade changed owner.
* the prompt's floor is **measured from its control rows** (`_prompt_floor`, 526 px today) and *is* real: a row of combos
  cannot reflow, and Tk widens a column rather than clip its children, so a smaller floor would not move the sash, it would
  snap back. That one changing with content is why the same drag stops in different places on different days.

**What changed.** Floors for strip and pane are now a constant **120** px (findable, but no bigger than the reason needs)
and the caps are gone: a column grows until the window stops it. Verified by jumping each boundary to both ends in a
1600 px window - strip 618 -> 1116 (pane at its floor) and -> 480/120 the other way, gallery -> 120 at one end, prompt
526 -> 860 at the other. The prompt floor is left measured, deliberately, and documented as the only limit that is not
arbitrary. The tile grid already reflows to whatever width it is given (`_contents_metrics`), so no detent work was needed
for the pane to stay usable at 120 px.

## 19. Sessions: dividing a folder by when the work happened (2026-11-02)

Asked after a btw thread proposed time rather than prompt as the axis for a 500-picture folder. The reader's objection was
that it must be **manual**, so the module was built to propose seams and never apply them by itself.

**The measurement that decided the rule** (real gallery, 2,925 pictures over 11 days):

| model | result |
|---|---|
| sessions = runs with no gap >= 4 h | 20 over 11 days, median 3 h 28, longest 14 h 59 |
| sessions crossing midnight | **4 of 20** - a calendar cut splits one night's work in two |
| gaps >= 8 h | 9 -> 10 periods, about one per day |
| gaps >= 10-12 h | 5 -> 6, too coarse: it skips days |
| largest gaps *end* | 07:40 - 12:36 (the night ends when he wakes, not at 00:00) |

So the rule is **cut in the gap, not on the clock**: a candidate seam is the midpoint of every break at or above a
threshold (default 8 h) - the middle of an empty night belongs to neither side.

**`sessions.py`** is that rule as pure functions: `seams()`, `split()`, `label_for()`, and `load_cuts`/`save_cuts` in
`.zimage-sessions.json` at the gallery root. A cut is a **timestamp**, never an index, because a picture added later with
an earlier time must land in the right session instead of shifting every later segment down one; and it carries no
decision about the pictures, so the partition is reversible by deleting one entry. Segments are keyed for storage by the
**root prompt** (`key_for`), not the label - the label is a medoid and moves when content changes, which is exactly the
folder that gets split.

**Wired** (v0.18.0): right-click the open folder's title -> *Split into sessions* / *Merge the sessions back*. The plan is
expanded into **sibling folders** (`<family> · Sun 01 Nov 22:00`), so tiles, pane, paging, ranking and A/B review need no
change. The raw plan is kept (`_plan_raw`) so splitting recomputes from the families and can never nest.
Verified end to end on a synthetic two-night gallery: one folder -> two session folders, the cut stored at the gap
midpoint, merge restores the single folder. `test_sessions.py` asserts the invariants (every item exactly once, stability
under a newer picture, undated pictures kept, per-folder storage isolation, rename keeps identity).

**Not built, deliberately**: per-picture "start a new session here" (today a split accepts *all* seams at once), gap marks
drawn between tiles, an N-equal split, editable session labels, and a settings control for the threshold. The design for
each is in the conversation, not the code.

## 24. Why the window stops drawing during a run, and what is not yet fixed (2026-11-02)

Asked how to stop the UI thread hanging while a matrix or a render runs. The rendering itself was never the problem:
`engine.generate` is threaded and progress arrives through `ui_events`. The blocking is what runs **between** pictures, on
the UI thread:

| work | cost | when |
|---|---|---|
| `refresh_gallery` inside `show_fresh_result` | **476 ms** measured (v0.20.0) | once per finished picture - 21 freezes in a matrix |
| pane page build (`render_contents`) | 160-315 ms | per folder open or re-scope |
| thumbnail decode on the pane's first page | 3.6 ms/tile cold (346 ms per 96) | cold cache |

**Fixed:** `show_fresh_result` coalesces that rebuild to **once per 1.2 s** while a driven run is in flight
(`_run_in_flight`), with a final flush after it. Measured in a simulated matrix: five finished pictures cost **3** strip
rebuilds instead of 5 - better, but not the one-per-window the code intends, because a second path (`select_folder` on a
newly created folder, and `_regroup_soon` when the plan does not yet know the picture) refreshes too. That attribution is
the next step, not a guess.

**Not fixed, and the real answer to the question:** a 476 ms synchronous rebuild on the event loop will always show as a
stall whenever it runs. The structural fixes, in order of value: make `refresh_gallery` cheap (it is `PLAN §11.2`: the scan
behind a folder click), build the pane page in chunks so no single callback exceeds ~100 ms, and move the cold thumbnail
page off the UI thread (page 2 already prefetches; page 1 does not).
