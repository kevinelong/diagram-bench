## 2. What changed in the GUI (committed as `35aebaf`, suite green)

Three changes, each one variable and each with the suite run after it.

1. **Destroyed-tile guard** (3 sites, `_scroll_folder_into_view`, `_see_folder`, one more). A strip rebuild
   leaves a queued callback holding a dead Tk window path — that is the `TclError: bad window path name`
   in `%LOCALAPPDATA%/zimage-ui/errors.log` from 2026-10-30, and it is why scrolling/clicks feel dead for a
   moment after any refresh.
2. **The open folder now stays open after a render.** `_show_new_results` used to close it so the brand-new
   (unfiled) picture would be visible; that read as "the folder will not open after a generation". The hint now
   says where the picture is. This was a *tested contract* — three assertions in `test_gallery_ui.py` were
   rewritten to the new behaviour, explicitly.
3. **The seed box advances by the batch, not by one.** `generate()` records `_seed_advance = batch * seed_step`
   (or `seed_step` for a true single-latent batch); the save handler consumes it **once** and resets it to 1.
   A 16-up from seed N now leaves the box at N+16; it used to leave N+1, so the next press re-rendered 15 of
   the same 16 seeds. New coverage: "a 16-up from seed 900 leaves the box at 916".
   The one-shot reset is load-bearing: without it, any save that did not go through `generate()` inherited the
   last batch's step (the suite caught exactly that: 793 instead of 778).

Not changed, and deliberately: `_show_new_results` closing behaviour was reverted once because
auto-reopening the folder inside `_apply_plan` changes what `app._files` holds and broke `test_gallery_ui.py:3649`
with `IndexError`. The adaptive poll (60 ms -> 200 ms idle) was also reverted: it starved the suite's ~50 ms
`root.update()` spins, and it was never proven to be the idle-lag cause.

## 3. Performance instrumentation (P0+P1 of the plan, done)

- `ZIMAGE_TIMING=1` enables; `ZIMAGE_TIMING_LOG` overrides the path (default
  `%LOCALAPPDATA%/zimage-ui/timings.log`). **Verified: off by default, no file written when off.**
- Format: JSON Lines, `{"t","ev","ms","own","kids","d"}`. Nesting is attributed, so a slow parent reports its
  children's share.
- Ten timed sites: `refresh_gallery`, `render_folder_tiles`, `render_folder_bar`, `render_contents`,
  `render_empty_pane`, `apply_strip_resize`, `enlarge`, `show_image`, `thumbs_for`, `folder_sheet`.
- `timed_panel` is defined above `thumbs_for` on purpose: `thumbs_for` is at line ~917 and a decorator must
  exist when its `def` runs. `timed` and `_TIMING` resolve at call time, so they stay lower in the file.

### Cold-start prewarm (added, not yet proven)

`_prewarm_thumbs()` runs at the end of `refresh_gallery`, once per session, warming the 12 strip thumbnails plus
each folder tile's 4 in a worker thread. Rationale: a tile's PhotoImage is built on the paint path — 13 ms for a
cached-size thumbnail, up to 81 ms for a 6 MB 1536 px render — so a cold start was paying twelve decodes during
the first paint, which is the "twelve blank tiles" in the 2026-10-31 screenshot.
**It shows no delta in the suite** because that temp gallery's thumbs are already warm. Proving it needs a run
against a gallery with no `.thumbs` cache — do not delete the real cache without asking (3000+ files rebuild).

Also diagnosed from the same screenshot: the folder column is empty at start because grouping is still running
(~2.4 s for 1800 prompts). That is not a bug and cannot be hurried; only the blank *tiles* were a defect.

## 6. Gotchas worth keeping

- `ZIMAGE_NO_SETTINGS=1` disables persistence and fails 13 settings checks. Use `ZIMAGE_SETTINGS_DIR` pointing at
  a temp dir instead, or the run looks broken when it is not.
- The test suite builds the app as `zui.App(root, StubEngine(), args)` and drives it with `feed_image` / `click`;
  `feed_image` bypasses `generate()`, which is why batch behaviour had no coverage until today.
- Two edits dropped a function signature this session (`_folder_sheet`, then `_refresh_gallery`). `py_compile`
  after every edit caught both. Keep doing it.
- Do not "fix" a test to fit a change unless the change is a deliberate contract change — and then say so in the
  test's own words, as the three folder assertions now do.

### 8.1 The bug that started as "the panes look wrong"

A review window drew gradients I never wrote, at 325x190, for a file that is 64x64 and solid. Three measurements settled it,
in this order: PIL on the file (solid), `--probe b.png` (`64x64 … centre=(160,100,90)`), and a log inside `paint_pane`
(`…/zimage-review-selftest/gallery/b.png` — **the wrong folder**). The session key hashes picture *names*, so two folders
whose pictures are both `a.png`..`d.png` share one session file, and `build()` trusted the stored `paths`. Fixed in
`pair_review.build` and `review::build` (reset when the stored paths name a different folder) — `69314dc` — with a
regression test in `test_review_modes.py`: same key, own paths, no inherited decisions.

### 8.3 Things that will waste an hour if forgotten

- **PowerShell captures are DPI-virtualised.** `PrintWindow` of a 1100x760 window came back as 733x507 (1100 × 96/144),
  i.e. the top-left two-thirds — which looks exactly like a layout bug and is not. Call
  `SetProcessDpiAwarenessContext(-4)` in the capturing process first.
- **`cargo build` keeps the old exe while a running instance holds it**, and the failure is easy to miss behind a filtered
  grep: a log I had added never printed because the binary predated the edit. Compare exe and source timestamps.
- **The list header is a separate HWND**: without `DarkMode_ItemsView` it stays a light band across a dark list
  (`LVM_GETHEADER` → `SetWindowTheme`), and `WS_BORDER` draws the classic light client edge.
- The mnemonic goes on the **A**, not the B: `&A/B…` displays `A/B…`; `A&B…` displays `AB…`.
- A commit hook refuses a tree where modified Python files are left unstaged, and an *aborted* commit keeps its files
  staged: after a hook refusal, stage explicitly and check `git status` before the next `commit`.
