### The strip still refuses to compress — two experiments, both reverted

The strip canvas **requests** `width=GAL_ASK_W` (318 px) and a widget's request is a hard minimum, so the gallery column
measures ≥318 whatever the sash is told. That is why the pane obeys 106 and the strip does not. Two fixes were tried and
both were backed out, because each broke something larger:

| Attempt | Result |
|---|---|
| `width=1` (let the grid give the canvas its width) | window came up **899×585** with the prompt column empty — the column arithmetic depends on the request |
| `width=GAL_FLOOR_W` (106, the new floor) | **18 failures**, 5 newly broken, all in strip reflow: "a narrower window re-lays them out", "and so does a wider one", "and opening it again re-lays nothing either", "closing the folder re-lays nothing, because no width moved", "with a folder open the folder tiles are inside the strip canvas" |

So the canvas request is load-bearing in the reflow logic (`_on_strip_resize` / `_folder_geom_now` / `_render_folder_tiles`
all read the measured canvas width, and the assertions pin what a resize must not disturb). Lowering the strip floor to
106 is only half the job: the strip's reflow expectations have to be reworked **with** it, in the same change, or the
suite reports five regressions. State left at **13 failures, 0 new** with the strip defect documented rather than
half-fixed.

## Environment and harness traps (each cost time this session)

- **Git Bash cannot exec the venv python** (`command not found` though the file exists). Use PowerShell/cmd, or
  `MSYS_NO_PATHCONV=1 cmd.exe /c "…\.venv\Scripts\python.exe …"`.
- **The venv `python.exe` is a launcher that re-execs the base interpreter**, so `zimage_ui.py` shows up as *two* pids —
  the window belongs to the `C:\Python312\python.exe` child. Kill by command line, not by window title:
  `Get-CimInstance Win32_Process | ? { $_.Name -eq 'python.exe' -and $_.CommandLine -like '*zimage_ui*' }`.
- **`Start-Process` with `-RedirectStandard*` hangs the shell** — the child inherits the handles and the job never ends.
  Launch without redirection; read stderr from the app's own logs instead.
- **`curl` straight to `D:\models\comfyui\…` intermittently dies with exit 23** (write error). Download to `%TEMP%`, then
  copy.
- **`pip install --index-url …/cu130 torch spandrel` aborts entirely** — spandrel is PyPI-only, so pip refuses the whole
  resolve. Two commands: torch/torchvision from cu130, spandrel from PyPI.
- **torch must be cu130** or `comfy_kitchen` reports the cuda backend `disabled: True`. (Enabled did not make renders
  faster — the nvfp4 weights are still emulated on Ada — but it is the supported configuration.)
- **Screenshots of the app need the window raised**: `SetWindowPos(HWND_TOPMOST)` + `SW_RESTORE` + `SetForegroundWindow`,
  otherwise you capture whatever is on top (a ChatGPT window, in this session). Script:
  `%TEMP%\diagram-smoke\capture.ps1`.
- **`_fill_pending` swallows per-label exceptions** by design (one bad tile must not stop a paint), so a test shim that
  forgets `root`/`_photo`/`_photo_of` reports `False` and looks like the bug. Bind all four before concluding.
- **`test_sizing.py` is not a usable gate on this box**: `& .venv\Scripts\python.exe test_sizing.py` (~75 s) reports 14
  failures on pristine `master` because floors (1603) exceed the 1280 px screen. Compare failure *sets*, never counts
  alone. `git worktree` was unreliable here (directory vanished) — use a second clone instead.
